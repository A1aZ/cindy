## 1. 背景

schedule 任务通常由自动化持续产生，数量远高于用户主动创建并长期交流的普通任务。用户主要关心它是否运行、是否成功、结果摘要和是否需要处理，而不是长期在手机内存中保留每次运行的完整消息。

当前 Mobile 对打开过的任务采用接近一致的消息驻留和缓存策略。大量 schedule 任务被逐个打开后，完整消息、流式状态、渲染投影和本地消息缓存可能持续累积；后台运行产生的消息还会放大列表更新和临时对象分配。

本方案将 schedule 任务按“通知摘要 + 按需详情”处理：列表长期保留轻量摘要，完整详情只在用户正在查看时存在，离开后激进回收。

> **与 Issue-2726（手机端打字或发送消息时经常闪退）的关系**：本方案是内存驻留治理，属于降压手段之一，不诊断也不承诺修复闪退根因。若闪退根因在输入法、渲染层或其他路径，需另行定位；本方案只保证 schedule 任务不再持续放大内存压力。对普通任务的内存减压见 §9.1 的现状说明。

## 2. 目标

1. schedule 任务数量增长时，Mobile 中完整消息的驻留量不随已打开任务数持续增长。
2. 用户仍能在列表看到运行状态、未读状态、结果或错误摘要，并能随时重新打开详情。
3. 普通任务保持现有使用体验，并补上内存治理：非活跃单任务最多 80 条、普通任务合计约 800 条全局预算、其余按 LRU 淘汰（阶段 4 实施；当前基线对普通任务的内存消息**没有任何回收治理**，见 §9.1）。
4. 分类和回收逻辑集中在少量入口，不引入升级状态、多层 TTL、独立 schedule 消息预算或自动归档状态机。
5. 首版只修改 Mobile。若实现必须触及脚本、Desktop、共享包或协议，先暂停并单独说明，不混入本方案。

## 3. 范围与非目标

### 3.1 本方案范围

- Mobile 内的普通任务 / schedule 任务二分类。
- schedule 任务的详情加载、订阅、失焦和重新打开行为。
- schedule 任务完整消息、流式内容、渲染投影和 Mobile 本地消息缓存的回收。
- 防止迟到请求或推送在回收后重新灌入完整消息。
- 普通任务的消息内存治理：非活跃单任务 80 条、全局约 800 条预算、LRU 与保护清单（阶段 4）。
- 对应的 Mobile 单元测试和流程测试。

### 3.2 本方案不做

- 不删除、归档或修改工作设备上的真实任务、消息和 schedule 运行历史。
- 不改变 Desktop 行为。
- 不改变 Device Link、IPC、推送事件或其他跨端 wire protocol。
- 不解决 `sessions:list` 的 200 条目录额度被大量 schedule 任务挤占的问题。
- 不解决当前 `schedule.list()` 后执行 `N × listRuns(..., 50)` 的同步效率问题。
- 不增加服务端选择性订阅能力；首版只约束 Mobile 收到数据后的驻留和渲染。
- 不为普通任务引入新的状态机、定时器 TTL 或独立预算体系；普通任务治理复用统一分类与回收入口（阶段 4），不另起炉灶。
- 不改变普通任务的交互与使用体验；治理只影响不可见时的内存驻留量。
- 不修改原生依赖、Expo 配置、runtime fingerprint、数据库 schema 或 migration。

上述目录额度和同步效率问题如果后续要处理，应另开方案；它们可能需要 Desktop、共享契约或 Device Link 配合，不能作为本次 Mobile-only 实施的隐含扩展。已识别的优化方向与依赖边界记录在 §17。

## 4. 不可变二分类

Mobile 中只存在两种任务保留策略：

- **普通任务**：按对话型任务处理，保留有限历史并参与全局 LRU 和消息预算。
- **schedule 任务**：按通知型任务处理，长期只保留摘要，完整详情按需加载并在离开后激进回收。

任务类型由创建来源决定，生命周期内不可变：

| 场景 | 分类 |
| --- | --- |
| 用户或普通流程创建的任务 | 普通任务 |
| schedule 的 fresh 模式为单次运行创建的任务 | schedule 任务 |
| schedule 的 `persistentSession` 模式创建并持续复用的任务 | schedule 任务 |
| schedule 通过 `targetSessionId` 绑定的既有普通任务 | 普通任务 |
| 用户回复、置顶、重命名 schedule 任务 | 仍是 schedule 任务 |
| schedule 任务正在运行、等待处理或已读 / 未读 | 仍是 schedule 任务 |

不增加 `promoted`、`converted` 等第三种状态。用户对 schedule 任务的任何操作都不会把它升级为普通任务；运行态只决定当前是否能立即释放某些运行时对象，不改变分类。

### 4.1 Mobile 分类依据

分类应由一个 Mobile 内部的纯函数统一完成，列表、详情页、Store 和缓存层不得各自判断。

**判据只有任务的稳定来源字段 `session.source === 'scheduler'`**。这个判据成立的原因：

- Desktop scheduler 对 fresh 和 persistent 两种模式的会话创建走同一 `createSession` 路径，统一带 `vendorOptions: { source: 'scheduler' }`（`apps/desktop/src/main/scheduler-host/runner.ts`）。
- bound 模式（`targetSessionId` 指向既有会话）的目标会话保留用户创建时的原始 source，不会被改写。

1. `session.source === 'scheduler'` → schedule 任务。
2. 其余情况（包括出现在 schedule 索引中、带 schedule 未读、由 schedule 触发运行的绑定任务）→ 普通任务。
3. 无法确认时保守按普通任务处理。

**legacy `[Schedule] ` 标题前缀不再识别**（2026-08-15 裁决：老版本命名已废弃）。老数据里 source 缺失、标题带前缀的会话按普通任务保守处理——方向是多驻留而不是误回收；且标题会被用户重命名，作为分类依据本来就不稳定（整体 review P1-5）。

**分类不得依赖 schedule 索引或 `schedule.list` 的新鲜度**：schedule 索引是 30s TTL + 失败负缓存的“晚半拍”次要数据（`scheduleIndex.ts`），分类若依赖它，索引加载失败会把任务拖成“无法分类”。source 字段随 `sessions:list` 一次性到达，分类只读它。

用于列表展示的 schedule 索引可以同时包含“schedule 生成的任务”和“被 schedule 绑定的普通任务”，因此**不能直接把 schedule 索引是否命中当作回收分类依据**。现有 `isAutomationSession` / 首页 `isAutomationSession`（`mobileHome.ts`）为分组展示目的把“索引命中”也算进自动化——分类函数**不得复用这些展示辅助**，需要新写更严格的判定。

## 5. schedule 任务的数据模型

schedule 任务拆成两层数据：

### 5.1 常驻通知摘要

列表和后台状态只保留现有能力可提供的紧凑信息：

- 任务和工作设备标识。
- schedule 名称或任务标题。
- 最近运行时间和运行状态。
- 未读数量 / 已读状态。
- 结果摘要或错误摘要。
- 是否正在运行、是否需要用户处理。

摘要应优先复用现有 session 元数据、schedule index、run 的 `status`、`resultText`、`errorMsg`、`readAt` 等字段。若 Mobile 需要增加投影，只增加 Mobile 本地类型，不修改共享协议。

摘要允许截断，只用于列表展示和决定是否提醒；它不承担完整详情恢复职责。

### 5.2 按需完整详情

完整详情包括：

- 最近消息窗口。
- 正在生成的流式内容。
- 消息渲染投影和工作过程详情。
- 仅详情页需要的任务更新、上下文和临时 UI 状态。

这些数据只在该 schedule 任务详情页当前可见时驻留。重新打开时，从工作设备重新读取最新消息窗口，不依赖上次离开后仍保留完整正文。

## 6. 具体生命周期行为

### 6.1 列表中但从未打开

- 展示通知摘要、未读和运行状态。
- 不主动加载完整消息。
- 不建立该任务的完整消息订阅。
- 后台事件只更新对应任务的轻量摘要，不为预览重建完整消息列表。

前两条在当前基线已是现状（只有打开过详情的任务才会把完整消息种入 Store，列表行只用 session 预览），本条的意义是**把它们固化为不回退的行为约束**，而不是新机制。

### 6.2 打开详情

1. 将该任务标记为当前详情驻留任务，并建立新的详情代际。
2. schedule 任务不从长期消息缓存 hydrate 完整正文。
3. 从工作设备加载最新消息窗口；首版仍复用现有单次 80 条窗口，不新增 schedule 专属页大小。
4. 页面获得焦点后订阅该任务的实时消息和运行状态。
5. 页面可见期间，行为与普通任务详情一致，用户可以阅读、回复和处理交互。

### 6.3 失焦、切换任务或离开详情

按以下顺序收口：

1. 使当前详情代际失效，禁止迟到的读取结果写回。
2. 取消该任务的完整消息订阅。
3. 完成必须的草稿、outbox、上传和乐观发送状态交接。
4. 调用统一回收入口，释放完整消息和详情运行时状态。
5. 删除该 schedule 任务在 Mobile 的完整消息缓存。

回收完成后的目标状态是：非当前 schedule 任务的完整消息驻留量为 0，只保留任务目录元数据、通知摘要以及安全发送或交互所需的最小状态。

### 6.4 App 进入后台

schedule 详情按“已经不可见”处理：停止完整消息订阅，并在安全状态交接后回收完整详情。回到前台且页面再次获得焦点时，重新从工作设备加载。

触发挂点必须同时覆盖三处（与现有已读回执的 AppState 门槛同构）：

1. `useFocusEffect` cleanup——覆盖导航离开 / 切换任务；
2. AppState listener（`active` → 其他状态）——锁屏 / 切后台时导航焦点不变，`useFocusEffect` 的 cleanup 不会跑，只有这里能兜住；
3. 会话切换（同页换 `sessionId`）——effect 闭包持旧 sessionId 收尾。

只挂导航焦点一处的实现是不完整的。

### 6.5 后台运行中的 schedule 任务

“正在运行”不保护完整消息正文：

- 保留 running 状态、结果 / 错误摘要、未读和必要交互提示。
- 非当前详情页不保留流式全文和完整消息数组。
- 如果全局推送带来消息内容，Mobile 只提取或更新摘要；没有详情驻留权限时不得把正文写回长期消息 Store。

### 6.6 重新打开

- 列表行和通知摘要仍然存在。
- 重新取得详情驻留权限并加载最新消息窗口。
- 加载期间可以显示现有的加载态或摘要，不展示已经被回收的旧正文快照。
- 工作设备离线时，摘要仍可见，但完整详情可能暂时不可用；这是通知型缓存策略的明确取舍。

## 7. 回收内容与保护内容

### 7.1 激进回收的内容

- 完整消息数组。
- 流式文本 head、合批定时器和流式拼接中间状态。
- 消息渲染投影、工作过程投影和仅详情可见的任务更新。
- 可重新从工作设备读取的上下文、分页游标和临时详情状态。
- Mobile AsyncStorage 中该 schedule 任务的完整消息缓存。

### 7.2 始终保留的轻量内容

- 任务目录元数据和设备归属。
- schedule 任务分类依据。
- 通知摘要、未读、最近运行状态和时间。
- 打开任务所需的 session ID / schedule ID 映射。
- 独立存储的最小 pending interaction 信息。

### 7.3 不得误删的本地工作

回收不得丢失：

- 未发送草稿。
- outbox 和仍在途的发送请求。
- 未完成的附件上传。
- 尚未得到远端确认的乐观消息所需状态。
- 未解决的用户交互请求。

若 pending interaction 已经有独立数据模型，应只保留该最小对象而回收完整消息；如果现状仍必须依赖消息正文才能安全处理，则暂缓释放相关最小消息片段，直到交互解决。这个保护只影响能否立即清理局部数据，不改变任务类型，也不让整段历史长期驻留。

## 8. 单一分类入口和单一回收入口

为控制维护复杂度，实现只新增两个概念：

1. `regular | schedule` 的统一分类函数。
2. 统一的任务运行时回收入口，根据分类和回收原因选择保留项。

不得为 schedule 任务再实现一套平行 Store、缓存或生命周期状态机。

**注意：当前基线没有任何统一运行时回收入口。** 早前迭代曾在 `remoteSessionStore.ts` 实现过 `releaseSessionRuntimeState` / `compactSessionMessages`，但那批改动因方向偏差已整体还原，HEAD 中不存在这两个函数。本方案需要**新建**统一回收入口（可参考已还原实现的设计教训，特别是其中两个已识别的正确性问题：乐观归档失败无法完整恢复、把列表缺失误判为已删除——见 §10.2），例如传入 `retentionKind` 和 `reason`，由入口统一处理：

- 消息和流式状态释放。
- 订阅 / 定时器清理。
- 本地完整消息缓存清除。
- 草稿、outbox、上传和 pending interaction 保护。
- 任务目录元数据和摘要保留。

页面、列表和事件处理层只表达“任务已失焦”“App 进入后台”“当前任务改变”等事实，不自行拼接清理步骤。

## 9. 内存和本地缓存策略

### 9.1 普通任务

**现状（2026-08 基线）：普通任务的内存消息没有任何回收治理。** 打开过的任务完整消息在 Store 中无限驻留；只有磁盘缓存（AsyncStorage）按会话限制在 80 条（`MAX_CACHED_SESSION_MESSAGES`）。此前一版（已还原）实现过“离页压回 80 条”的方向正确部分，本方案的阶段 4 把它作为完整策略补回。

阶段 4 实施后的普通任务治理规则：

- **单任务上限**：非活跃普通任务最多保留 80 条消息（与 `MESSAGE_PAGE_SIZE`、磁盘缓存上限对齐）。离开详情页、切换任务时触发压缩。
- **全局预算（双维度）**：所有普通任务合计进入「约 800 条 **或** 估算内存 64MB 任一超限」的全局预算；超出时按最近访问时间 LRU 回收非保护任务的消息。字节维度是病态分布的兜底——device-link 的 push 截断是整帧超限后的紧凑预算（160K 字符/帧）而非单条上限，读取路径也不受它约束，病态大行堆积时条数完全不设防；典型分布（每条几 KB）下字节维度永不触发。估算按消息对象缓存（WeakMap，不可变替换的消息每个版本只算一次），口径为 UTF-16 字符 × 2 + 结构常数（对 ASCII 实际高估约一倍，保守方向），只求量级正确。
- **保护清单**（以下任务不参与压缩与 LRU 淘汰）：当前详情任务；正在运行的任务；有待处理交互（pending interaction）的任务；有本地在途工作的任务（未发送草稿所在任务、outbox 未清空、附件上传未完成、乐观发送未获远端确认）。
- **触发时机**：挂在统一回收入口的既有调用点（离开详情、切换任务、App 进入后台），**不引入独立定时器或周期扫描**。
- **压缩的语义边界**：只释放“可从工作设备重新读取”的完整消息、渲染投影和流式中间态；不碰任务目录元数据、未读状态、pending interaction、草稿与 outbox。绝不做“列表缺失即删除”（§10.2 红线同样适用）。
- **恢复路径**：压缩后重新打开走现有“磁盘缓存优先、远端对账”路径（缓存本就只存 80 条），不需要新增恢复机制；运行中受保护任务不压缩，无恢复问题。

schedule 任务的当前详情可临时计入全局预算并作为当前任务受保护；一旦失焦直接回收到 0（§9.2），不占用预算、不参与 LRU。

### 9.2 schedule 任务

- 当前可见详情最多加载现有 80 条消息窗口。
- 非当前详情的完整消息目标驻留量为 0。
- 不建立 schedule 专属消息条数预算或另一套 LRU。
- schedule 当前详情不占普通任务预算、不参与 LRU：驻留窗口有界（≤80 条），一旦失焦直接回收到 0，不等待预算触发（实现上 schedule 会话在预算记账前即跳过，两维度都不计入）。
- schedule 任务不写入长期完整消息缓存；如果旧版本已留下对应缓存，在该任务被识别或离开详情时按现有 key 定点清除。
- 不增加一次性迁移脚本。历史磁盘缓存采用惰性清理：任务被识别为 schedule 后删除其缓存；登出时仍由现有全量清理覆盖。

## 10. 异步竞态与正确性红线

### 10.1 详情驻留权限

每次进入 schedule 详情都生成新的 generation / authority token。以下异步结果写 Store 前必须同时满足：

- session ID 仍是当前任务。
- 页面仍有焦点且 App 仍处于允许详情驻留的状态。
- generation 与请求发起时一致。

失焦、切换任务、进入后台或显式回收时立即使 generation 失效。迟到的消息读取、缓存 hydrate、订阅回调和流式合批不得让已回收任务重新驻留完整消息。

**写入围栏的明确例外**：失焦后在途的发送确认（乐观消息的远端回执）、outbox 落定结果和交互回执，允许写回安全交接保留的最小状态（发送状态、pending interaction 的结果），但不得据此重新驻留完整消息数组或触发缓存回写。围栏挡的是“完整正文复活”，不是“在途事务收尾”。实现时要逐条核对 `remoteSessionStore` 的消息写入路径（`applyRemoteEvent`、`mergeMessages`、`hydrateMessagesIfEmpty`、流式 flush、乐观发送确认），确认哪些路径属于例外、哪些必须被围栏拦截，并各配测试。

### 10.2 部分列表不代表删除

**筛选、分页或 200 条限制下未返回某个任务，不代表任务已删除。**

因此：

- 不能通过“本轮列表中不存在”触发任务数据清理。
- 只有明确的服务端 removal / deleted 事件、设备移除、Store 重置，或本方案定义的 schedule 详情失焦回收，才能调用对应清理路径。
- schedule 激进回收只清理 Mobile 运行态和消息缓存，不移除任务目录元数据，更不删除远端数据。

### 10.3 绑定普通任务不得误回收

`targetSessionId` 可能指向用户已有的普通任务。该任务即使出现在 schedule index、带有 schedule 未读或由 schedule 触发运行，也必须继续走普通任务保留策略。

## 11. 普通任务与 schedule 任务行为矩阵

| 行为 | 普通任务 | schedule 任务 |
| --- | --- | --- |
| 分类是否会变化 | 不会 | 不会 |
| 列表常驻数据 | 元数据、预览、状态 | 元数据、通知摘要、状态 |
| 打开详情 | 加载 / hydrate 有限历史 | 从工作设备按需加载最新窗口 |
| 实时完整消息订阅 | 按热任务和页面策略 | 仅当前可见详情 |
| 失焦后的消息 | 压回 80 条；全局约 800 条预算 + LRU（阶段 4） | 安全交接后回收到 0 |
| 后台运行 | 可按通用热任务策略保留 | 只保留轻量运行摘要 |
| 未读 | 可保护预览和必要历史 | 只保护入口、摘要和红点 |
| 回复、置顶、重命名 | 仍为普通任务 | 仍为 schedule 任务 |
| 本地完整消息缓存 | 保留最近窗口 | 不长期保留，失焦定点清除 |
| 重新打开 | 优先缓存后远端对账 | 重新从工作设备读取 |
| 远端真实数据 | 不受本地回收影响 | 不受本地回收影响 |

## 14. 实施顺序

### 阶段 1：分类与回收入口

- 新增统一二分类函数（主判据 `session.source`，见 §4.1）。
- 明确 fresh、persistent 和 bound 三种 schedule 模式的归属（作为测试口径与 source 缺失时的 fallback 判定）。
- 将 schedule 详情回收接入现有统一清理入口。
- 先补分类和数据安全测试。

### 阶段 2：详情生命周期与缓存

- schedule 详情获得焦点时按需加载和订阅。
- 失焦、切换任务、卸载和 App 后台时撤销驻留权限。
- 跳过 schedule 完整消息缓存，并清理旧缓存。
- 保留草稿、outbox、上传和 pending interaction 的安全状态。

### 阶段 3：事件写入围栏与回归验证

- 为读取、订阅和流式合批增加 generation / authority fence。
- 非当前 schedule 事件只更新通知摘要。
- 验证普通任务消息预算、缓存和交互行为没有变化。

### 阶段 4：普通任务消息治理

在 schedule 逻辑验证稳定后实施，复用阶段 1 的统一分类与回收入口（`retentionKind` 的第二种策略），不新增平行机制：

- 离开详情、切换任务时把非活跃普通任务压回 80 条。
- 普通任务合计约 800 条全局预算，超出按 LRU 回收非保护任务。
- 保护清单：当前任务、运行中、待处理交互、有本地在途工作的任务（§9.1）。
- 触发点只挂统一入口既有调用时机，不引入定时器或周期扫描。
- 补对应测试（§15.5）并回归验证压缩后重开、缓存对账、运行中不压缩等行为。

## 15. 测试与验收标准

### 15.1 分类

- fresh schedule 创建的任务判为 schedule 任务。
- `persistentSession` 创建并复用的任务始终判为 schedule 任务。
- schedule 绑定的既有 `targetSessionId` 始终判为普通任务。
- legacy `[Schedule] ` 标题不再识别：source 缺失的老任务保守判为普通任务（2026-08-15 裁决）。
- 分类不依赖 schedule 索引：索引未加载 / 加载失败 / 只命中绑定任务时，分类结果不变。
- schedule 任务被回复、置顶或重命名后仍按 schedule 策略回收。
- 运行中、等待处理、成功、失败和已读状态都不改变分类。

### 15.2 生命周期和内存

- 连续打开并离开大量 schedule 任务后，Store 中不累计这些任务的完整消息数组。
- 任意时刻只有当前可见的 schedule 详情可驻留完整消息；失焦后的目标值为 0。
- 后台运行的 schedule 任务持续更新状态和摘要，但不持续增长完整消息 Store。
- App 进入后台后，schedule 详情订阅和可回收运行态被释放；返回后可重新加载。
- schedule 逻辑（阶段 1–3）落地期间，普通任务行为与改动前基线一致。

### 15.3 缓存和恢复

- schedule 任务不会新增长期完整消息缓存。
- 旧版本留下的该任务缓存能在识别或失焦时定点删除。
- 回收后列表行、摘要、未读和运行状态仍存在。
- 重新打开时能从工作设备恢复最新详情。
- 工作设备离线时不会展示被误认为最新的旧正文。

### 15.4 数据安全和竞态

- 草稿、outbox、在途发送、附件上传和未解决交互不会被错误清理。
- 迟到的读取、hydrate、订阅回调和流式合批不会让已回收任务重新驻留。
- 受筛选、分页或 200 条限制影响而未出现在列表中的任务，不会被当作已删除。
- 回收操作不会删除或归档工作设备上的任务、消息和运行历史。

### 15.5 普通任务消息治理（阶段 4）

- 普通任务离开详情后消息压回 80 条；重新打开能从磁盘缓存与远端对账恢复，不丢任务元数据、未读和 pending interaction。
- 普通任务合计超过约 800 条时，按 LRU 回收最近最少访问的非保护任务消息。
- 当前详情任务、运行中任务、有待处理交互的任务、有草稿 / outbox / 在途上传 / 乐观发送未确认的任务不被压缩或淘汰。
- 运行中的普通任务后台持续产生消息时不被压缩；运行结束后再次离开详情才压缩。
- 压缩与预算回收不会把“本轮列表未返回”的任务当作已删除（§10.2 红线同样适用）。
- schedule 任务不占用普通任务预算、不参与 LRU；schedule 当前详情失焦后立即归零而不是压回 80 条。

## 16. 已知代价

- schedule 详情离开后再次打开需要重新读取，首屏速度和离线可读性会弱于普通任务。
- 首版仍受现有 schedule index 和 50 条 run 窗口限制；较老 legacy 任务（source 缺失）保守走普通任务策略。
- 首版只降低 Mobile 的消息驻留和缓存，不减少工作设备推送的数据量，也不解决目录被 schedule 任务占满的问题。

这些代价是“通知型 schedule 任务 + Mobile-only + 低维护复杂度”边界下的有意取舍。若实际数据表明需要提升离线详情、目录容量或协议效率，应分别立项，不在本回收策略上继续叠加例外状态。

影响边界（分阶段交付期间）：**阶段 1–3 只回收 schedule 任务的内存驻留**，此期间普通任务的内存仍无治理；阶段 4 落地后普通任务的累积才受到 80 / 800 / LRU 约束。对 Issue-2726 这类闪退问题，本方案（含阶段 4）是降压手段之一，不构成根因修复。

## 17. 关联优化方向（另行立项）

首页 / 列表拉取链路的已知成本不在本方案治理范围内，本节把它们记录下来，明确依赖边界，避免后续重复分析或被当作本方案的隐含扩展。

### 17.1 现状已有的缓解（不需要本方案介入）

- schedule 索引按 key 单飞 + 30s TTL 节流 + 失败负缓存（`scheduleIndex.ts`），索引加载失败有熔断恢复旁路和逐设备离线失效。
- `listRuns` 刻意串行执行而非并发，避免 N 个后台读挤占会话打开的关键读（device-link 是无优先级的单 WS 管道）。
- 索引本身是 defer 的“晚半拍”次要数据，不挡首屏。

### 17.2 待优化方向

| 痛点 | 优化方向 | 需要动的模块 | 依赖边界 |
| --- | --- | --- | --- |
| `sessions:list` 200 条目录额度被大量 schedule 任务挤占 | 列表分页；或 schedule 任务在目录层折叠聚合（列表行收敛为 schedule 维度） | Desktop 查询 + device-link 契约 | 跨端；涉及协议兼容评审（`docs/dev-rules/protocol-compatibility.md`） |
| `schedule.list()` 后 `N × listRuns(50)` 的同步成本 | 协议级请求优先级（issue #324）；或聚合端点一次返回索引所需数据 | device-link 协议 | 跨端 |
| 后台运行推送携带全量正文，Mobile 只用得上摘要 | 服务端选择性订阅：非当前详情只推摘要级更新 | Desktop + device-link | 跨端；与本方案 §10.1 的 Mobile 侧围栏互补——本方案已保证“收不到正文也能正确”，该优化减少的是管道流量 |

### 17.3 本方案对这条链路的影响

中性偏好：分类零新增请求（`session.source` 已在 `sessions:list` 返回中）；schedule 任务不再 hydrate / 缓存正文后，首页预览对这些任务统一走 device-link 自带的 `session.preview`，行为更一致。

### 17.4 已知限制：渲染层内存不受任何预算约束

条数与字节预算都只作用于原始消息对象（`remoteSessionStore` 的 messages map）。渲染层的派生状态——markdown AST、消息渲染投影、图片解码缓存——不在两个预算内，其量级可能与原始消息相当甚至更大。消息被淘汰后渲染投影可被 GC 间接释放，但没有直接上限。若实测表明渲染层是主要压力源，需在渲染层另行立项（投影级 LRU 或可见窗口化），不在本方案上叠加。

另两条字节维度的已知限制（review 登记）：

- **首扫 stringify 尖峰**：首次预算检查对未缓存的对象型 content（tool_use/tool_result JSON）在同步循环里 stringify，瞬时分配约等于对象 content 总量（上界受 64MB 预算自身约束）；字符串 content 走 length×2 零分配路径。触发点在失焦/后台而非渲染热路径，可接受；将来如有需要可换无字符串的递归估算。
- **驻留中的 schedule 详情不计入字节预算**：窗口有界（≤80 条）、失焦即归零，实际驻留内存最多比预算多一个 schedule 窗口；预算检查只挂在普通任务触发点上，schedule 失焦的下一次普通任务失焦才会顺带评估。

### 17.5 已知限制：暂缓回收的收口依赖页面生命周期（GPT-5.6 整体 review P1-1/2/3/6，后续重构）

在途本地工作门禁暂缓回收期间与之后，存在四个已评估、暂接受的缺口，共同指向同一个架构级后续重构——**会话级在途工作跟踪与可见性 authority 拆分**：

- 门禁暂缓时驻留权不撤（在途发送确认需要写回，是设计取舍）；暂缓窗口内非可见页可累积正文。
- 驻留围栏是 boolean 而非 §10.1 字面要求的 generation token：blur→快速 refocus 后，撤销前发起的读取响应可提交旧窗口（数据真实、后续 load 会刷新，危害有界）。严格 token 需要动 requestSync 链路。
- 原地切会话/卸载时被暂缓的旧会话没有观察者补回收（页面级 1→0 观察者随实例销毁或改绑新会话）；后果仅内存驻留、无增长，重复操作可跨任务累积。
- 全局预算淘汰看不到其他会话的页面级在途工作（outbox/上传/乐观发送）；草稿在独立 store 不受影响，实际暴露面是栈下层会话这类边缘路径。

完整修法：按 sessionId 的 local-work registry（页面当前任务门禁与全局预算候选筛选共用）+ 可见性 authority 与破坏性回收拆开（blur/background 无条件推进 generation 并标记补载，破坏性回收可暂缓）+ per-session generation token。属一次重构，不在本 PR 范围内。
